# Context access (runtime optimization)
Read `stage_context_analyze.json` once. The bundle uses original filenames as keys and contains their complete contents. References below to individual JSON/text inputs mean their entries in that bundle. Do not redundantly run file listings, read the same file again, or perform ad-hoc schema validation: the CLI enforces `--output-schema` and Python handles QA. If bundle data is missing, consult the original input file only when essential. Keep all evidence, source and editorial rules below unchanged.

Analyze the attached contact sheet images. The frames are labeled FRAME001 etc, and the machine-readable frames.json in the current directory includes approximate timestamps. Do NOT assert functions based only on HUD symbols. Do NOT infer what the programmer was inspired by or claim Slope3 originally created an established game IP. Provide en-US JSON with fields defined by analysis.schema.json.

When game_brief.json is present, its name, site/game URLs and PC/mobile controls are owner-confirmed product inputs. Do not guess another title or ask again about those controls. Keep nonempty idea_origin, story and game_style as the owner's editorial outlines and propose research topics/images that support that direction. Empty optional fields authorize creative development later; do not turn a supplied outline into invented historical evidence.

Read brand_context.json. The owner's declared developer role is trusted context for this supplied product, not something to disprove based on missing frame evidence. Keep exact identity guesses separate from ownership: resemblance to a known game does not confirm its title. Do not invent historical inspiration in the analysis. Propose research topics that can become a coherent real-world starting point for our creative product concept, closely connected to visible movement, setting and visual choices.

Tasks: (1) infer a likely game title or "Unknown Game"; (2) list visible objects, environment, score/HUD, and player actions demonstrably apparent, (3) list controls, mobile support, character names, power-up effects as unverified unless visually demonstrated, (4) propose 3-5 culturally relevant real-world research queries and 3-5 Wikimedia photo search topics; do not fabricate sources. Return only JSON.

Build a DETAILED `game_objects` inventory, not just a short gameplay summary. Inspect ALL attached contact sheets and enumerate distinct visible object types: player characters, enemies/NPCs, each meaningful obstacle type, collectibles, possible power-ups, track/terrain structures, interactive objects, scenery/landmarks, and HUD/menu/result components. Use 12-25 entries when the footage genuinely supports that breadth; simple games may have fewer. Do not invent objects or split cosmetic duplicates to reach a quota.

Each object needs id (OBJ001...), descriptive name, category, appearance, observed_behavior, supporting frame_ids, confidence (high/medium/low), needs_confirmation, and question. Distinguish object identity from inferred function: a visible icon is not proof of a power-up effect. When its name/function is unclear, describe its shape and set needs_confirmation=true with a concise question for the developer. The next stage can show a form for missing details, so prefer an explicit question over a guessed function.

For every object, write question in English and its faithful natural Vietnamese translation in question_vi. Keep both empty when nothing needs confirmation. Both versions appear side by side for the Vietnamese-speaking developer; preserve all subquestions and uncertainty.

The unverified_mechanics list contains concise English questions about genuinely unknown product details. Return a parallel unverified_mechanics_vi list with the same count and order, translated faithfully into natural Vietnamese. Do not ask again about controls, title or facts explicitly supplied in game_brief.json or confirmed owner_answers.json. Produce both language versions in this same response, without a separate translation task.

DISCOVERY QUERIES: Supply 4-5 short, distinct, relevant concept names in research_topics (usually 1-6 words), such as 'Mosaic', 'Polyomino', 'Tessellation' and 'Tiling puzzle' for a geometric block game, or suitable concepts for the actual video. These strings go directly to Wikipedia search. Do not write requests such as 'Search for research on...' or long research proposals. image_search_topics must likewise contain short visual search phrases for this game's concept, without the redundant words 'Wikimedia Commons'. Do not add urban/train imagery to a game without that setting.
OUTCOME RULES: Explicitly inspect objective, success/win or endless-score goal, how progress is achieved, rewards after success, exact game-over/loss trigger, and consequences after loss (restart, score reset, lives or other penalties). Separate observed facts, owner-confirmed facts, and unknowns. If any materially missing rule is not already in game_brief/owner answers/memory, add a precise question with Vietnamese translation to unverified_mechanics. A five-minute clip without an ending is not evidence of a win condition or absence of penalties. Never assume levels, prizes, lives, time limits or game-over rules. For an endless game confirm that there is no final win rather than inventing one.

For every game object also provide name_vi, appearance_vi and observed_behavior_vi: faithful Vietnamese display translations of name, appearance and observed_behavior. Generate these in this same analysis call. Preserve uncertainty; these translations are not additional evidence or owner confirmations.

CONTROL COMPLETENESS: Read the owner-provided PC/mobile controls first. Determine which exact input operates each core action: key/button name or touch gesture, target, press-versus-hold/release where relevant, direction and visible result. Ask one concise bilingual clarification only for essential missing details, not details already supplied or saved. Do not infer arrow keys, WASD, Space, rotation, restart shortcuts, swipe or pinch from a similar game. The final Controls section must let a first-time player perform their first move.
